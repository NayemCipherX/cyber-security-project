System Documentation

Technical specifications, software requirements, database planning and interface documentation for the CyberShield AI project.

1. System Specification

CyberShield AI is designed as a web-based cybersecurity research prototype. The proposed application will use a browser-based interface, a server-side application layer, a machine learning component and a cloud service layer.

Specification Proposed Selection
Application Type Web-Based Security Monitoring Prototype
Frontend HTML, CSS and JavaScript
Backend PHP
AI Component Python and Machine Learning
Database MySQL / AWS RDS
Cloud Platform Amazon Web Services

2. Functional Requirements

Functional requirements describe the operations that the proposed application should support.

  • FR-01: The system should provide secure user authentication.
  • FR-02: Authorized users should be able to access the monitoring dashboard.
  • FR-03: The system should accept and process supported security event records.
  • FR-04: The machine learning component should produce threat classification results.
  • FR-05: The application should maintain security event records.
  • FR-06: Configured threat conditions should be able to trigger AWS SNS notifications.
  • FR-07: Administrators should be able to review authorized security records.
  • FR-08: The application should support security reports and event investigation.

3. Non-Functional Requirements

These requirements describe the quality, reliability and security expectations of the proposed system.

  • Security: Protect user accounts, credentials and application data.
  • Performance: Process supported events within reasonable response times.
  • Reliability: Handle errors without silently losing important event records.
  • Scalability: Allow the architecture to accommodate increased event volume.
  • Usability: Provide a clear and understandable dashboard interface.
  • Maintainability: Keep application components organized and documented.
  • Availability: Design cloud components for dependable access and operation.

4. User Roles and Permissions

User Role Responsibilities
Administrator Manage authorized accounts, review system records and configure security settings.
Security Analyst Review alerts, investigate suspicious events and examine reports.
Standard User Access permitted dashboard information and view authorized reports.

These are proposed application roles. Actual permissions will be implemented using role-based access control.

5. Database Design

The proposed relational database will maintain application users, security events, model predictions, notification records and administrative activity.

Table Important Fields Purpose
users user_id, username, email, password_hash, role User accounts and access roles
security_events event_id, event_type, source, timestamp, status Collected security records
threat_predictions prediction_id, event_id, predicted_class, confidence Machine learning output
alerts alert_id, event_id, severity, notification_status Security notification records
audit_logs log_id, user_id, action, created_at Administrative activity history

This is a proposed logical schema. Data types, constraints, indexes and relationships will be finalized during database implementation.

6. Database Relationship Overview

  • One user may generate multiple audit log records.
  • One security event may have one or more analysis records.
  • One security event may produce multiple alert records.
  • Each alert should reference its related security event.
users | |---- audit_logs security_events | |---- threat_predictions | |---- alerts

7. Proposed API Specification

The backend may expose authenticated API endpoints for communication between the web interface, application server and detection component.

Method Endpoint Purpose
POST /api/login Authenticate a user
GET /api/events Retrieve authorized security events
POST /api/events Submit a security event
GET /api/alerts Retrieve alert records
GET /api/reports Retrieve available reports

These are proposed endpoint designs, not currently deployed API routes.

8. Authentication and Data Protection

  • Store passwords using secure password hashing.
  • Validate and sanitize incoming application data.
  • Use HTTPS for production communication.
  • Protect API endpoints with authentication and authorization.
  • Use IAM roles and least-privilege policies for AWS access.
  • Never expose AWS access keys in frontend source code.
  • Record sensitive administrative actions in audit logs.

9. Error Handling and Logging

The application should handle invalid input, failed authentication, unavailable services, database errors and notification delivery failures. Error records should include useful diagnostic information without exposing passwords, credentials or sensitive user data.

10. Deployment Considerations

The current public website is hosted through GitHub Pages and serves static HTML, CSS and JavaScript. The PHP backend, Python detection service and database will require a separate server or cloud deployment environment.

Production deployment will require environment configuration, secure secret management, database connectivity, access policies and testing of cloud integrations.
